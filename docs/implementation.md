# Реализация и ограничения

## Пакетная переливка

Паттерн: staging → проверка → атомарная публикация. CSV читается потоково, строки передаются COPY, а справочники и связанные таблицы наполняются пакетными SQL INSERT SELECT. Временная staging-таблица удаляется при завершении транзакции. Единовременный advisory lock запрещает двум загрузчикам одновременно публиковать один набор.

Проверяются SHA-256, число строк, даты, суммы, сроки и уникальность идентификатора строки. Публикация данных и load_run проходит в одной транзакции. При ошибке частично загруженные рабочие таблицы не остаются. Повтор той же версии по двум хешам возвращает already_loaded. Другой снимок нельзя молча смешать с текущим: требуется новая база. Это сохранение неизменной версии источника и идемпотентная начальная загрузка, а не полноценная SCD2-история изменения каждого атрибута.

Тексты названных преподавателем файлов «паттерны_переливка_и_версионирование.md», «паттерны_разделение_нагрузки_репликация» и чек-лист семинара 14 не предоставлены. Реализация соответствует распространённому staging-паттерну; точное совпадение с отсутствующей методичкой пока не подтверждено.

## Серверная логика

credit_risk принимает ID и год: UNKNOWN при отсутствии выручки, HIGH при долг/выручка > 0,5, MEDIUM при > 0,25, иначе LOW. Это прозрачное учебное правило, не банковская скоринговая модель.

BEFORE-триггер loan_limit берёт отчёт за календарный год до даты одобрения. Кредит ровно в 50% выручки допускается; превышение и отсутствие отчёта дают SQLSTATE 23514. Дополнительный триггер запрещает изменение отчёта, нарушающее лимит существующего договора. Проверка использует блокировку строки отчёта FOR SHARE; конфликтующие обновления отчёта ожидают завершения транзакции. Любой deadlock или serialization failure требует отката и повтора всей бизнес-транзакции на стороне приложения.

SECURITY DEFINER-функции используют фиксированный search_path, полные имена таблиц и отозванный PUBLIC EXECUTE. Владельцем остаётся доверенный создатель стенда. Обычный пользователь не получает права менять код функции.

Обычное представление вычисляется при чтении; materialized view хранит результат и требует REFRESH. Первый REFRESH выполняется после загрузки, последующие могут быть CONCURRENTLY благодаря уникальному индексу borrower_id. Витрина намеренно отражает состояние на момент последнего обновления. Права на REFRESH остаются у владельца БД; credit_admin — ограниченный администратор приложения.

## EXPLAIN и кэш

PostgreSQL обычно не кэширует готовые результаты SELECT. Он использует shared_buffers, файловый кэш ОС и может сохранять планы подготовленных запросов. DISCARD ALL очищает состояние сессии, но не shared_buffers и не кэш ОС. Поэтому нельзя называть его очисткой всех данных из кэша.

В приложенном эксперименте до и после индексов одинаковые данные, PK/UNIQUE и настройки; дополнительные пять индексов отсутствуют в первой фазе. Перед каждой фазой VACUUM ANALYZE. Первый запуск каждого запроса — прогрев, затем три измерения; сравнивается медиана. SQL не использует prepared statements; JIT и параллелизм одинаково отключены в обеих фазах. Полные планы с BUFFERS/SETTINGS/ANALYZE сохранены в JSON. Это сравнение в установившемся режиме, **не cold-cache тест**. Индексы не навязываются через enable_seqscan=off.

Требование файла об удалении запроса из кэша технически неоднозначно. Для строго холодного теста нужен отдельный управляемый стенд со сбросом shared_buffers и кэша ОС перед каждым замером. На пользовательском компьютере глобальный кэш не сбрасывался. Метод измерения и это ограничение необходимо назвать на защите.
